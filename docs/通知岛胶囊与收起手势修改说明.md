# 通知岛胶囊与收起手势修改说明

## 涉及的功能

锁屏通知岛（胶囊岛 / 展开的通知列表）与「从列表收起回胶囊」的手势，以及胶囊岛图标的内容来源。

不涉及：音乐播放、封面/歌词、壁纸、时钟、息屏显示等其它功能。

## 问题现象

1. 胶囊岛左边显示的图标不是列表里最新那条通知的图标，新通知来了图标也不换。
2. 通知列表上滑过之后，往下拉有时会直接收起（第一条还没滚回来），有时又怎么拉都收不起来。
3. 收起动画看不出「倒叙」：不是离岛最远的那条先进岛。

## 原因与修改

### 1. 胶囊岛图标改用列表里最新那条通知的图标

文件：`app/src/main/java/com/os4/musiccover/LockIslands.kt`（`aggregate()`）

原因：胶囊的图标位图在 `MiniPlayerRuntime.noteBitmap()` 里按 `key + note.time` 缓存。合计岛的 key 固定为 `mc:stack`，而 `time` 取的是「领头那条」的时间；当最新那条由于属性/优先级排序不是领头时，`time` 不变，缓存一直命中，画出来的始终是旧图标。

修改：

- 合计岛的文案保持原样（`通知` / `N 条通知`），只有图标改成该堆通知里时间最新那条（`members.maxByOrNull { it.time }`）；
- 最新那条没有图标时回退到领头那条的图标；
- 合计岛的 `time` 由「领头那条的时间」改为 `maxOf(lead.time, newest.time)`，新通知到达时缓存才会失效。

影响：只影响胶囊岛左侧图标与它所对应的缓存时间；列表内容、文案、点按行为不变。### 2. 图标位图缓存同时看时间和图标对象

文件：`app/src/main/java/com/os4/musiccover/MiniPlayerRuntime.kt`（`noteBitmaps` 声明与 `noteBitmap()`）

原因：缓存只比对 `time`。同一条通知换了图标、或合计岛换了「最新那条」而时间恰好没变时，旧实现会继续用缓存的旧图。

修改：缓存值由 `Pair<Long, Bitmap?>` 改为 `Triple<Long, Drawable?, Bitmap?>`，命中条件加上 `icon === note.icon`。

影响：图标更新更及时，不改变其它绘制逻辑。

### 3. 下拉先滚列表，第一条回来了再收岛

文件：`app/src/main/java/com/os4/musiccover/MiniPlayerRuntime.kt`（`releasedRowAt()`、`pullKeepsForList()`，以及静态转发 `MiniPlayerRuntime.pullKeepsForList()`）、`app/src/main/java/com/os4/musiccover/Main.java`（`cardSwipe()` 的 `ACTION_MOVE` 分支）

原因：原判定是「记住第一条的原位，再看它现在的位置」，但原位记录时机、行复用都会让它失准：记录偏了就一直收不起来，反之就一拉就收。

修改：手指按在通知行上时先记下那一条的屏幕位置；下拉超过触摸阈值（`1.6 × touch slop`）后看它有没有跟着手指走：

- 跟着走 → 列表还能滚，这一拉交给列表（先把第一条滚回来），不收岛；
- 没跟着走 → 已经在第一条，才调用 `collapseRow()` 把这一堆收进胶囊；
- 读不到那一条（没按下通知行）时按原行为处理。

影响：只影响通知行上的下拉手势；上滑滚动、点按打开通知、音乐卡自身的手势都不变。

### 4. 收岛按倒叙：离岛最远的那条先进岛

文件：`app/src/main/java/com/os4/musiccover/MiniPlayerRuntime.kt`（`pileStack()`）

原因：行的「趟次」是按离领头的距离排的（出岛时最近的最先出来）。往回收时沿用同一顺序，看起来就不是倒着收。

修改：往回收（`stackGoingHome()`）时把趟次反序（`if (stackGoingHome()) byLead.reversed() else byLead`）。

影响：只有通知岛收起时各行的先后。

### 5. verbose 下把收起轨迹写进日志

文件：`app/src/main/java/com/os4/musiccover/MiniPlayerRuntime.kt`（`trace()`）

原因：收起过程的轨迹只存在内存环形缓冲（`landTrace`）里，真机上排查只能靠它。

修改：`op verbose --ez on true` 打开后，`trace()` 同时 `Xp.log("[MCT] …")`。默认关闭，不影响日常使用。### 6. 顺带提交的探针（不是功能改动）

- `Main.java`：新增 `op nscroll`，读通知列表自己的滚动状态（`MiniPlayerRuntime.listScrollProbe()`）。
- `MiniCardMorph.kt`：新增只读属性 `isRunning`，给上面的探针用。

两处都只在手动执行探针时生效，不参与正常逻辑。

## 验证

- 编译：`./gradlew :app:assembleDebug --offline`，结果 `BUILD SUCCESSFUL`。
- 设备：`25098PN5AC`（pandora，Android 17 / HyperOS），`adb install -r` 覆盖安装（与设备上的签名一致，无需卸载），随后重启 SystemUI 让模块重新加载。
- 实机观察：锁屏胶囊岛显示 `通知 / N 条通知` 的合计文案，左侧图标随最新那条通知变化；在展开的列表上下拉，先把第一条滚回来，再次下拉才收进胶囊。
- 抓取方式：`op mini` / `op fold` / `op rowtree` 探针 + `uiautomator dump` 读锁屏文本。

## 已知问题（本轮未处理）

设备上偶发「音乐卡在 mini 与 native 之间来回切」：日志里 `dynamic choice -> native (pulled)` 与 `dynamic choice -> mini (out of the scene)` 交替出现（约每秒一次，随曲目变化触发），切换时通知岛会跟着上下移动。本轮改动没有触及这条路径。
